# Objective

Refactor the prompt-enhancement feature to improve its reliability, responsiveness, and user-facing feedback while strictly preserving existing behavior and outputs.

The change must be behavior-preserving: the enhanced prompts produced, the API interactions performed, and all existing functionality must remain identical except for the specific UX and performance improvements described below.

Deliver three coordinated improvements: \(1\) a clear, non-technical toast notification when a user reaches their hourly usage limit; \(2\) simplified, user-friendly error messaging that removes technical or misleading text from failure paths; \(3\) reduced enhancement latency plus a visible loading indicator on the canvas while enhancement is in progress.

## Requirements

- Detect when the user has exhausted their hourly usage allowance and display a toast informing them they have reached their limit for this hour and can try again later.
- Ensure the limit-reached toast uses plain, non-technical language only; it must not expose internal identifiers, quota numbers, headers, status codes, or any implementation details.
- Replace the current error string 'An invalid response was received. Please try again.' with the shorter message 'Try again.' so users are not shown misleading or redundant wording.
- For any subsequent or remaining errors after that replacement, show a generic, user-friendly feedback message instead of raw error output, stack traces, or technical diagnostics.
- Ensure prompt enhancement honors the user's stated intent exclusively: the enhanced output must contain only content derived from the user's input and intent, with no added unnecessary details, filler, or extraneous information.
- Optimize the enhancement pipeline to reduce end-to-end latency so the AI enhancement step no longer takes excessively long \(e.g., streamline request construction, remove redundant processing steps, avoid blocking work on the main path\).
- Add a simple spinner/loading indicator on the canvas that is shown while the prompt is being enhanced and hidden once enhancement completes or fails.

## Verification

- Provide regression evidence demonstrating that enhanced-prompt output is unchanged for representative inputs before and after the refactor, confirming behavior preservation.
- Verify the hourly-limit scenario by simulating limit exhaustion and capturing the exact toast text shown, confirming it matches the intended friendly wording and contains no technical details.
- Verify the error path by forcing the previously seen invalid-response condition and confirming the UI now displays 'Try again.' instead of the old message.
- Verify secondary/remaining error handling by triggering additional failures and confirming only generic, user-friendly messages appear, with no raw errors leaked to the UI.
- Verify intent fidelity by comparing enhanced outputs against user inputs across multiple intents and confirming no unrelated or unnecessary content was added.
- Measure and report enhancement latency before and after optimization to demonstrate a measurable reduction in time-to-result.
- Confirm the spinner appears promptly when enhancement starts, remains visible during processing, and disappears on both success and failure.

## Constraints

- Do not alter public contracts, exported APIs, component interfaces, or data shapes consumed elsewhere; all existing callers must continue working without modification.
- Preserve backward compatibility of the enhancement request/response flow; changes must be limited to internal structure, messaging strings, and presentation.
- Do not degrade performance elsewhere: the added spinner and toast logic must not introduce noticeable overhead, layout shifts, or blocking work.
- All user-facing messages must remain non-technical and must never disclose internals such as quota values, rate-limit headers, provider names, status codes, or system configuration.
- Keep the scope bounded to the described UX, messaging, and latency improvements; do not add new features, new dependencies, or unrelated refactors.
- Maintain accessibility of the new spinner and toasts \(e.g., appropriate roles/announcements\) without changing existing accessible behavior of other components.
